## 1. The big picture

A backend does one job: it waits for a request, does some work, and sends a response. Everything in this folder serves that loop, plus one more question: **what happens when something goes wrong?**

```text
Browser / curl
   |  HTTP request
   v
server/main.go       starts everything, stops it safely
   |
   v
handler/router.go    middleware chain: RequestID -> Logger -> Recovery -> route
   |
   v
handler/*.go         thin: read request, call service, write response
   |
   v  (service layer comes later)
store/               talks to PostgreSQL using SQL
```

### Map from JS to Go

| Go (this project) | JS you already know |
|---|---|
| Gin middleware (`c.Next()`) | Express `app.use((req, res, next) => ...)` |
| `context.Context` | `AbortController` / `AbortSignal` |
| `select` on channels | `Promise.race` |
| Go `interface` | TypeScript structural types |
| `config.Load()` | a zod-validated `process.env` |
| `go.mod` | `package.json` |

### File map

```text
backend/
├── server/main.go                  entry point, wiring, graceful shutdown
├── internal/
│   ├── config/config.go            read and validate env variables
│   ├── handler/
│   │   ├── router.go               routes + middleware order
│   │   ├── middleware.go           RequestID, Logger, Recovery
│   │   ├── problem.go              one error format for the API
│   │   └── health.go               /healthz and /readyz
│   └── store/

├── sqlc.yaml                       tells sqlc where things are
├── .air.toml                       live reload
└── .golangci.yml                   linter rules
```

## 2. `server/main.go`

### `main` calls `run`

`os.Exit(1)` skips every `defer`. If `main` did the work and exited on error, the database pool would never close. So `run` **returns** an error, and `main` only reports it. This is a very common Go pattern.

### `slog`

Go's built-in structured logger. It writes JSON lines like:

```json
{"level":"INFO","msg":"request","status":200}
```

Machines can search JSON. Plain `fmt.Println` text is much harder to search.

### Startup order

| Step | Code | Why |
|---|---|---|
| 1 | `config.Load()` | Fail at startup on bad settings, not at 3 a.m. on a user request. |
| 2 | `gin.SetMode(ReleaseMode)` in prod | Quieter, faster Gin. |
| 3 | `signal.NotifyContext(...)` | Creates a `ctx` that is cancelled on Ctrl+C (SIGINT) or Docker stop (SIGTERM). Like an `AbortSignal` wired to the operating system. |
| 4 | `store.NewPool(...)` | Opens a pool of database connections. Opening one is slow (network + login), so you do it once and reuse. |
| 5 | `defer pool.Close()` | Runs when `run` returns. `defer` means "do this when the function ends, however it ends". |
| 6 | `http.Server{...}` | The actual web server. |

### The server timeouts

```go
ReadHeaderTimeout: 5 * time.Second,
ReadTimeout:       10 * time.Second,
WriteTimeout:      15 * time.Second,
IdleTimeout:       60 * time.Second,
```

Without timeouts, a slow or broken client can hold a connection forever. Enough of them and the server runs out of resources (called a *slowloris* attack).

`Handler: handler.NewRouter(...)` works because Gin's engine has a `ServeHTTP` method, so it satisfies Go's `http.Handler` interface.

### Goroutine + channel + `select`

```go
serveErr := make(chan error, 1)
go func() { serveErr <- srv.ListenAndServe() }()

select {
case err := <-serveErr:   // server crashed early (for example, port in use)
case <-ctx.Done():        // user pressed Ctrl+C
}
```

- `ListenAndServe` **blocks**: it never returns while healthy. So it runs in a goroutine.
- The main goroutine waits for whichever event happens first.
- The channel has size 1, so the goroutine can always send its result and exit, even if nobody is listening.
- New to channels? See [section 12](#12-go-concept-channels).

### Graceful shutdown

```go
srv.Shutdown(shutdownCtx)   // stop new requests, let running ones finish (max 10s)
<-serveErr                  // read the final result of ListenAndServe
```

`http.ErrServerClosed` is the normal answer after `Shutdown`, so only other errors count as failures.

The `defer` calls then run in reverse order. The pool closes **after** the server has stopped, which is the right order.

### `%w` error wrapping

```go
return fmt.Errorf("listen: %w", err)
```

This adds context ("listen: ...") but keeps the original error, so `errors.Is(err, X)` can still find it later.

## 3. `internal/config/config.go`

Settings come from **environment variables**, not from code:

- The same program runs on your laptop and on a server without code changes.
- Secrets (database password) stay out of git.

### Key ideas

| Idea | Where | Why |
|---|---|---|
| `type Env string` + constants | `EnvDev`, `EnvProd` | Like a TS union `"dev" \| "prod"`. Typos are harder to make. |
| Fail closed | `Env: EnvProd` default | A forgotten `APP_ENV` gives the safe mode, never the unsafe one. |
| `errors.Join` | end of `Load` | Reports all problems at once. You fix everything in one deploy. |
| Never print `DATABASE_URL` | error messages | It contains the password, and logs get copied around. A test checks this. |
| Returns `(Config, error)` | `Load` | Go has no exceptions for normal failures. The caller must check `err`. |
| Returns `Config{}` on error | last lines | A half-filled config can never be used by mistake. |

### Port check

```go
port, err := strconv.Atoi(v)
if err != nil || port < 1 || port > 65535 { ... }
```

`Atoi` turns text into a number. The range check follows the real limit of TCP ports.

## 4. `internal/store/postgres.go`

```go
pool, err := pgxpool.New(ctx, databaseURL)
...
pingCtx, cancel := context.WithTimeout(ctx, 5*time.Second)
defer cancel()
if err := pool.Ping(pingCtx); err != nil { ... }
```

- `pgxpool.New` does **not** connect yet. Without the `Ping`, the app would "start fine" and fail on the first real request.
- `context.WithTimeout` gives a context that cancels itself after 5 seconds. A dead database cannot hang startup forever.
- `defer cancel()` releases the timer. Always call `cancel` after `WithTimeout`.
- If ping fails, `pool.Close()` cleans up before returning the error.

The package name `store` has a rule: **all database access lives here**. No other layer writes SQL.

## 5. `internal/handler/`

The handler layer is **thin**: parse the request, call business logic, format the response. No business rules here.

### `router.go`

- `gin.New()` (not `gin.Default()`): you choose every middleware yourself.
- `SetTrustedProxies(nil)`: clients cannot fake their IP with an `X-Forwarded-For` header.
- `r.Use(RequestID(), Logger(logger), Recovery(logger))`: **order matters**. The request ID must exist before the logger and recovery read it.
- `r.NoRoute(...)`: unknown paths also return the standard error shape.

### `middleware.go`

Middleware wraps a request like an onion. Code before `c.Next()` runs on the way in. Code after it runs on the way out.

```text
RequestID (in) -> Logger (in) -> Recovery (in) -> handler
RequestID (out) <- Logger (out) <- Recovery (out) <- handler
```

| Middleware | What it does | Why |
|---|---|---|
| `RequestID` | Makes a random ID per request, stores it, returns it in the `X-Request-ID` header. | A user says "request abc123 failed" and you find the exact log line. It ignores client-sent IDs, because clients could forge log entries. |
| `Logger` | Starts a timer, calls `c.Next()`, then writes one log line. | Logs `URL.Path` only, never the query string, so `?token=secret` never reaches logs. Status 500+ logs as `ERROR`. |
| `Recovery` | `defer` + `recover()` catches a panic, logs the stack trace, returns a clean 500. | Go's `net/http` survives handler panics, but it just drops the connection. This sends the client a proper response without leaking internals. |

`Recovery` re-panics for `http.ErrAbortHandler`, because `net/http` uses that panic on purpose to abort a response.

### `problem.go`

One error format for the whole API (RFC 9457 "Problem Details"):

```go
type Problem struct {
    Type   string `json:"type"`
    Title  string `json:"title"`
    Status int    `json:"status"`
    Detail string `json:"detail,omitempty"`
    Code   string `json:"code"`
}
```

- `json:"..."` tags set the JSON field names.
- `omitempty` hides `detail` when it is empty.
- `Code` is a **stable** string like `not_found`. The frontend switches on it. `Title` and `Detail` are for humans and may change.
- Rule in the comment: never send internal error text to the client. Attackers learn from error messages. Log the detail, send a generic message.

### `health.go`

| Endpoint | Question it answers | Checks database? |
|---|---|---|
| `/healthz` (liveness) | Is the process alive? | **No.** If it did, a database outage would make the orchestrator restart your app, which fixes nothing. |
| `/readyz` (readiness) | Can this instance serve traffic right now? | **Yes.** |

`Pinger` is a one-method interface:

```go
type Pinger interface {
    Ping(ctx context.Context) error
}
```

`*pgxpool.Pool` has a `Ping` method, so it fits automatically (no `implements` keyword, like TypeScript). Tests pass a fake instead of a real database.

This is **dependency injection**: `Ready(db)` receives what it needs instead of creating it. `Ready` returns a function that remembers `db` (a *closure*).

> `Ready` is your Day 1 exercise (`TODO(you)`).

## 6. SQL, sqlc and `store/gen/`

### Migration: `0001_init.up.sql`

```sql
CREATE TABLE users (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email TEXT NOT NULL UNIQUE,
  ...
);
```

| Piece | Why |
|---|---|
| `UUID ... DEFAULT gen_random_uuid()` | IDs that cannot be guessed (unlike 1, 2, 3). |
| `TIMESTAMPTZ` | Time with timezone. Avoids timezone bugs. |
| `NOT NULL`, `UNIQUE` | The database itself refuses bad data, even when the code has a bug. |
| `REFERENCES users(id) ON DELETE CASCADE` | Foreign key. Deleting a user deletes their sessions. |
| `token_hash` | Only a **hash** of the session token is stored. If the database leaks, attackers still have no usable tokens. |
| `CREATE INDEX sessions_user_id_idx` | Postgres does not index foreign keys automatically. Without this, "find sessions of user X" scans the whole table. |

The `down.sql` file undoes the `up` file. Migrations are **version control for your database structure**.

### Queries: `db/queries/users.sql`

```sql
-- name: CreateUser :one
INSERT INTO users (name, email, password_hash) VALUES ($1, $2, $3)
RETURNING *;
```

- `:one` = one row back. `:exec` = no rows back.
- `$1, $2, $3` are placeholders. Values travel **separately** from the SQL text. This is what prevents SQL injection.

Two queries worth studying:

- **`GetValidSessionWithUser`** uses `now()` from the database, so app and database never disagree about time. It selects only `name` and `email`, so `password_hash` cannot leak.
- **`DeleteSession`** needs both `token_hash` **and** `user_id`, so one user cannot delete another user's session.

### sqlc

```text
sqlc.yaml + migrations + queries/*.sql   --sqlc-->   internal/store/gen/*.go
```

You write real SQL. The tool generates type-safe Go. You never edit `gen/` ("DO NOT EDIT"). Run `make generate` after changing SQL.

### Reading the generated code

```go
row := q.db.QueryRow(ctx, createUser, arg.Name, arg.Email, arg.PasswordHash)
var i User
err := row.Scan(&i.ID, &i.Name, &i.Email, ...)
```

`Scan` needs the **address** (`&`) of each field so it can write database values into them. This is your pointer knowledge at work.

`DBTX` is a small interface that both a connection pool and a transaction satisfy. `WithTx(tx)` lets the same queries run inside a transaction. You will need this for balances, where several writes must **all succeed or all fail**.

## 7. Tests

| Technique | Example | Why |
|---|---|---|
| Table-driven tests | `tests := []struct{...}` + `t.Run` | Adding a case is one line. |
| `httptest.NewRecorder` | `serve(t, router, GET, "/healthz")` | Runs a handler with no real network or port. Fast. |
| Fake dependency | `fakePinger` | Stands in for the database. It fails if the code pings without a deadline, so a hang bug cannot hide. |
| `t.Setenv` | `config_test.go` | Sets an env var and restores it after the test. |
| `TestMain` | `gin.SetMode(gin.TestMode)` | One-time setup for the whole package. |

Test names follow `TestFunction_Scenario`, like `TestRequestID_IgnoresClientValue`.

Tests also check **security rules**:

- no leaked passwords in config errors
- no leaked panic text in responses
- no query strings in logs
- no forged request IDs

## 9. How to write code like this

The code is not clever. It comes from one habit: for every step, ask:

> **What can go wrong? Who needs to know?**

1. Write the plain happy path first (a server that answers `/healthz`).
2. Ask what breaks: bad config, database down, slow clients, Ctrl+C mid-request, a panic, a leaked secret.
3. Each answer becomes a small named piece:

| Question | Answer in this repo |
|---|---|
| What if settings are wrong? | `config.Load` with validation |
| What if a client is slow? | server timeouts |
| What if Ctrl+C hits mid-request? | `Shutdown` |
| What if a handler panics? | `Recovery` |
| What if errors look different everywhere? | `Problem` |
| What if the database is down? | `/readyz`, `Ping` at startup |
| What if a secret reaches the logs? | log path only, never print `DATABASE_URL` |

4. A function exists to **give an idea a name**, to **make it testable**, and to let **one thing change without touching others**.
5. Rules of thumb used here:
   - deciding is separate from doing (`config.Load` vs `main`)
   - I/O stays at the edges
   - dependencies are passed in as parameters

### Practice trick

Pick one line, delete it, and run the tests. See what fails. Each test exists because someone feared that bug.

## 10. Foundations to learn (in this order)

1. **How the web works.** HTTP methods, status codes, headers, JSON, ports, what TCP is. You know the client side. Now learn the server side.
2. **Processes and the OS.** Environment variables, signals, exit codes, stdout. This explains `main.go`.
3. **Go concurrency in full.** You know goroutines. Add channels, `select`, and especially `context`. Most real Go code uses `ctx`.
4. **Errors as values.** `%w`, `errors.Is`, wrapping.
5. **Databases.** Tables, primary and foreign keys, indexes, joins, transactions, and why pools exist. This is the biggest gap for most frontend developers.
6. **Security basics.** Hashing vs encryption, SQL injection, sessions, why secrets stay out of logs.
7. **Design basics.** Interfaces, dependency injection, layers, testing.

You do **not** need algorithms or a CS degree for this. You need items 1 to 7.

### Where to learn

- *Let's Go* by Alex Edwards: builds a real Go web app. Best match for you.
- [gobyexample.com](https://gobyexample.com): quick syntax checks.

## 11. Why frameworks exist, and your "gap"

You are not missing intelligence. You learned the **answers** (React, Nest, Django) without meeting the **problems** they solve. A framework is someone's repeated pain, packaged.

| Framework | Where it came from |
|---|---|
| Django | A newspaper team that needed to ship sites under daily deadlines. |
| Rails | Extracted from Basecamp. |
| React | Facebook's pain of keeping the screen in sync with changing data. Idea: UI is a function of state. |
| NestJS | Express gives no structure, and big teams needed one. |
| Gin | Every Go server needs routing, logging and recovery. This project's `Logger` and `Recovery` are things you would write in every server. |

Those engineers built the same thing many times by hand, felt the repetition, and extracted it.

### How to close the gap

**Build the pain first.**

1. Write a tiny server with only `net/http`, no Gin, with 3 routes.
2. Add logging to each route by hand.
3. Feel the repetition. Middleware will then make sense.
4. Repeat this once for each tool you want to understand.

This repo is already good practice, because every file answers a "what if it breaks?" question.

## 12. Go concept: channels

A channel is a pipe that lets one goroutine send a value to another goroutine safely.

```go
ch := make(chan int)   // a pipe that carries ints

go func() { ch <- 42 }()   // send: put 42 into the pipe

v := <-ch                  // receive: take a value out
fmt.Println(v)             // 42
```

### Blocking is the key idea

- A receive (`<-ch`) waits until someone sends.
- A send waits until someone receives.

So channels also make goroutines wait for each other, with no locks.

### Buffered vs unbuffered

| Kind | Code | Behavior |
|---|---|---|
| Unbuffered | `make(chan int)` | The send waits until a receiver is ready. |
| Buffered | `make(chan int, 1)` | Has room for 1 value. The send does not wait until the room is full. |

### Example in `main.go`

```go
serveErr := make(chan error, 1)
go func() { serveErr <- srv.ListenAndServe() }()
```

- The server runs in a goroutine. When it stops, it puts its error into `serveErr`.
- The main goroutine reads it with `<-serveErr`.
- The size is 1 so the goroutine can send and exit even if nobody is reading yet.

### `select`

`select` waits on several channels and runs the first one that is ready:

```go
select {
case err := <-serveErr:  // server failed
case <-ctx.Done():       // Ctrl+C (ctx.Done() is also a channel)
}
```

### JS comparison

| Go | JS |
|---|---|
| Channel | A promise that can deliver many values |
| `select` | `Promise.race` |
| A goroutine waits (blocks) | `await` and callbacks |

### Go's motto

> Share memory by communicating.

Instead of two goroutines changing the same variable (which needs locks), one goroutine sends the value to the other through a channel.
