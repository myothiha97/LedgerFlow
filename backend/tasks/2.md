## Objective: generate type-safe Go from hand-written SQL with sqlc.

The schema is applied and verified, so there is now something real to generate against.
No Go code can reach the database until the store layer has generated types and methods.
Every later layer (`domain`, `store`, `service`) imports what this step produces, so this
is the last piece of plumbing before you start writing actual Go logic.

## Your step

- Create `backend/db/queries/users.sql` and hand-write the SQL that Phase 1 registration
  and login need: insert a user, get a user by email, get a user by id, insert a session,
  get a session by its token hash, and delete a session.
- Create `backend/sqlc.yaml` at the Go module root. This is mechanical configuration with
  no Go-learning value, so ask me for it instead of spending the session on YAML.
- Point sqlc at `db/migrations` for the schema and `db/queries` for the queries, and send
  generated output to `internal/store/gen`.
- Run `make generate`, then get the module to compile again.

## Key context

sqlc never connects to your running database. It parses the migration files as its idea of
the schema, so those files are the truth it generates against. It understands golang-migrate
file naming and skips the `.down.sql` half on its own.

Each query needs a magic comment above it that gives the Go method a name and declares how
many rows come back. That declaration is what decides whether you get a single struct, a
slice, or no return value at all. A wrong declaration still generates successfully, it just
produces the wrong signature, so read what you got rather than assuming.

Three things about the current repository. `backend/internal/store/` does not exist yet, and
`backend/internal/handler/` is an empty directory. `backend/go.mod` has no pgx dependency, only
an unrelated indirect `lib/pq`, so generation will succeed and the build will then fail on a
missing import. That failure is the expected next move, not a mistake. And generated files are
overwritten every run, so never hand-edit anything under `gen/`.

Query the columns the specification actually defines. Do not invent a column that the
migration does not have, because sqlc will reject it rather than guess.
