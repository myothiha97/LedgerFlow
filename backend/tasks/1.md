## Objective: create and verify the first database migration.

This establishes a versioned and repeatable database schema for authentication. Every
later step depends on it: `db/queries/users.sql` and `make generate` produce Go from a
real schema, so `sqlc` has nothing to generate against until these tables exist. The
database is currently empty and `schema_migrations` has never been created.

## Your step

- Replace the placeholder content in `backend/db/migrations/0001_init.up.sql`.
- Write `backend/db/migrations/0001_init.down.sql`, which is currently an empty file.
- Add `users` and `sessions` tables. Column names, types, and rules are already
  specified in `docs/specifications/database-design-v1.md` section 4. Follow that
  table rather than redesigning it.
- Use UUID primary keys, `TIMESTAMPTZ` for every instant, a unique email, a unique
  session token hash, `ON DELETE CASCADE` from `sessions` to `users`, and an index on
  `sessions.user_id`.
- The down migration must drop `sessions` before `users`.

## Key context

golang-migrate treats the up and down files as one version. It applies the up file,
reverses it with the down file, and records the applied version in a `schema_migrations`
table it creates itself. Nothing checks that your down file actually reverses your up
file, which is why an empty down file is dangerous: the rollback reports success and
leaves the tables behind.

Sessions depend on users through a foreign key. That dependency fixes both the creation
order and the drop order, because PostgreSQL will not drop a table another table still
references. Creation and rollback are mirror images.

Three footguns for this step. PostgreSQL does not create an index for a foreign key
automatically, unlike a primary key or a unique constraint. PostgreSQL 16 can generate
UUIDs without installing an extension, so find the built-in function rather than
reaching for `pgcrypto`. Plural `snake_case` table names are a project rule and they
also avoid the reserved-word problem that a singular `user` table hits.

## Done means

`make migrate-up` applies cleanly. `\d users` and `\d sessions` show the unique
constraints, the cascading foreign key, and the index on `sessions.user_id`.
`make migrate-down` removes both tables, leaving only `schema_migrations` in `\dt`.
Running `make migrate-up` again succeeds, which proves the pair is repeatable.
